Getting Started

Quick Start: Running Any Laravel Project

Get up and running with PHP-Hyperion in under 60 seconds. You can run any existing or fresh Laravel 10, 11, or 12 project either without adding any files (automatic zero-config mode) or with hyperion_worker.php for full custom lifecycle control.

Build the optimized release binary directly using Cargo on macOS (Apple Silicon ARM64) or Linux (x86_64 / aarch64):

terminal — build & install 
# 1. Clone the repository
git clone https://github.com/Yassinidi/PHP-Hyperion.git
cd PHP-Hyperion/php-hyperion

# 2. Compile release binary with maximum compiler optimizations
cargo build --release -p hyperion-cli

# 3. Install globally into your system path (optional)
sudo cp target/release/hyperion-cli /usr/local/bin/hyperion

# 4. Verify installation
hyperion --version
# Output: ⚡ PHP-Hyperion v0.1.0 (Darwin ARM64 Apple Silicon)
✨

You do not need to touch or add any files to your Laravel codebase. Hyperion inspects the directory, detects artisan and bootstrap/app.php, snapshots the container, and starts serving with sub-millisecond speeds.

cd /path/to/my-laravel-project

Mode B: Custom Persistent Daemon via hyperion_worker.php
Use this mode when you want granular programmatic control over per-request lifecycle cleanups, multi-tenant database connection switching, custom singleton resets, or manual garbage collection triggers.
terminal — launch with custom worker

Architecture & Physics

Performance Physics: Micro-APIs vs Heavy SSR Pages

Why do lightweight APIs and micro-frameworks achieve 110,000+ req/s while full-stack SaaS landing pages (like thedevdojo/wave) achieve ~640 req/s? The answer lies in network bandwidth limits and pure CPU compute intensity.

🌐 1. Network Bandwidth Limits (85.7 KB vs 0.2 KB)

Pushing 100,000 req/s of an 85.7 KB page would require:
100,000 × 85,624 bytes = 8.56 GB/s = 65.33 Gbps!

No single server NIC or operating system socket buffer can push 65 Gbps without exhausting TCP buffers. At 642.9 req/s, Hyperion is streaming 53.8 Megabytes/second (~430 Mbps) of raw dynamic HTML generated on the fly.

⚙️ 2. CPU Compute Intensity (5.96 ms vs 0.015 ms)

On Wave's home page, every request executes:
• 7 SQL Database Queries (Plans, Settings, Categories, Posts)
• 30+ Nested Blade Components with inline SVG icons
• Livewire 3 HMAC Cryptographic Checksums

Warm render takes 5.96 ms of pure CPU time. On 4 cores: (1000ms / 5.96ms) × 3.8 cores ≈ 640 req/s. That is the physical CPU ceiling of raw un-cached rendering.

Kernel IPC Subsystem

Persistent IPC Pool & Zero-Race Worker Lifecycle

Hyperion decouples network concurrency from code execution. While Rust reactors handle thousands of concurrent client connections, requests are dispatched to dedicated, isolated PHP child processes over high-speed Unix Domain Sockets.

🔒 Zero Data Races via Multi-Process Isolation

Unlike threaded PHP runtimes (like FrankenPHP or pthreads) where requests run inside goroutines/threads sharing memory space, Hyperion maintains 100% separate operating system processes.

• At any millisecond, a worker executes exactly one request.
• No thread locks, no mutability collisions, and zero global variable bleeding.
• Native extensions like ext-gd, ext-pdo, and ext-redis run with 100% thread-safe deterministic behavior.

🐕 Active Supervisor Watchdog Loop

Hyperion’s Rust supervisor runs a dedicated background monitoring thread that polls all worker process IDs every 500 milliseconds.

• If a child process encounters a native segmentation fault or fatal error, the watchdog detects the dead PID immediately.
• A replacement worker is forked, booted, and connected in under 15 milliseconds.
• Incoming TCP client requests remain queued in the socket backlog with zero dropped connections.

♻️
Zero-Downtime Worker Auto-Recycling
To protect long-running services against memory fragmentation from third-party vendor packages, workers monitor their cumulative metrics. A worker gracefully self-terminates when it reaches either HYPERION_MAX_REQUESTS (default: 10,000) or HYPERION_MAX_MEMORY_MB (default: 512 MB). The supervisor seamlessly swaps in a fresh pre-warmed worker before retiring the old one.

High-Speed Caching Subsystem

RFC 9111 Generational In-Memory Caching

Hyperion integrates an in-memory RFC 9111 HTTP caching engine directly inside the Rust multi-reactor loop. Cached responses are served via zero-copy socket splicing at 208,036 req/s without waking up any PHP worker process.

1. Deterministic Invalidation

Whenever an HTTP mutation (POST, PUT, PATCH, or DELETE) executes on a resource, Hyperion instantly flushes all matching cache entries and subtree representations from RAM.

2. Set-Cookie Elimination

Per HYP-SEC-03, any Set-Cookie header emitted on a cacheable response is automatically stripped before storage, preventing session token leaks across different users.

3. Auth & Cookie Bypass

Requests carrying Authorization or Cookie headers immediately bypass the cache and pass directly to the dynamic PHP worker pool for individualized authentication.

Zend Engine Optimization

Memory Arena, Resident Footprint & Fiber GC

By compiling code once into Zend OPcache JIT memory and utilizing snapshot-based container state resets, Hyperion consumes 54.2% less RAM than standard PHP-FPM worker pools while processing over 200x more traffic.

🧠 Boot Arena State Snapshotting

During worker initialization, Hyperion executes the framework bootstrap phase (Composer class maps, environment files, Service Providers, compiled route tables) once.

• A memory pointer snapshot of the clean dependency injection container is stored.
• After each request terminates, singletons registered during the request lifecycle are unwound back to the pristine snapshot.
• Eliminates 25–50 ms of disk I/O and class autoloading on every single HTTP request.

♻️ Cyclic Garbage Collection Optimization

Zend’s default circular reference collector can cause unpredictable latency spikes when traversing massive object graphs.

• Hyperion automatically invokes gc_collect_cycles() in the background worker loop between requests.
• Unreferenced Eloquent model relations and event listeners are reclaimed before the next request arrives.
• Prevents gradual heap memory bloat across hundreds of thousands of request cycles.

Database Sizing, PgBouncer & ProxySQL Guide

When PHP processes requests in 0.35 milliseconds, traditional 1-to-1 database connections will overwhelm PostgreSQL or MySQL. You must size your connection pooling infrastructure accordingly.

🐘 PostgreSQL + PgBouncer (Transaction Mode)

Always deploy PgBouncer in transaction pooling mode. Connections are held only for the duration of a query/transaction and instantly returned to the pool:

pgbouncer.ini

[pgbouncer]
listen_addr = 0.0.0.0

pool_mode = transaction
max_client_conn = 2000
default_pool_size = 30
min_pool_size = 10
reserve_pool_size = 10
reserve_pool_timeout = 5

The Connection Sizing Equation
Optimal DB Pool Size = (Number of Hyperion Nodes × Workers per Node) ÷ Multiplex Ratio
For example: 4 Kubernetes nodes with 16 workers = 64 total workers. With PgBouncer transaction pooling multiplexing at 3:1, a pool size of 25–30 database connections easily handles over 95,000 requests per second with zero connection queuing.

🔄 Module 2: The Universal Persistent Worker Daemon (hyperion_worker.php)

Zero-Config Memory Persistence

Located at the root of the workspace (hyperion_worker.php). Boots any PHP framework (Laravel, Symfony, Slim, WordPress, Flight, or Vanilla) once into memory, stays resident, and processes binary IPC requests at 110,000+ req/s with zero cross-request state bleeding.

⚙️ Inside the 6-Stage Worker Execution Cycle

1. Cold Boot & Snapshot
Boots framework kernel, registers autoloader, warms up service providers, and freezes base container in memory.
2. Binary IPC Ingestion
Unpacks 16-byte binary wire frame from STDIN containing URI, HTTP method, headers, and request body.
3. Superglobals Reconstitution
Sanitizes and populates $_SERVER, $_GET, $_POST, $_COOKIE, $_FILES fresh for each request.
4. Kernel Pipeline Dispatch
Dispatches request through framework middleware stack, controller, and returns HTTP response object.
5. Output Capture & Wire Framing
Encodes status code, headers, and body into binary wire format and writes to STDOUT in a single sys-call.
6. State Sanitization & GC
Rolls back uncommitted PDO transactions, clears Auth guards, flushes query logs, and runs gc_collect_cycles().

Error Resolution

Production Troubleshooting & Error Codes

Diagnose and resolve common operational situations with exact error code mappings.

HYP-ERR-001: Worker socket connection timeout ▼
Cause: The Rust supervisor spawned a child worker process, but the worker could not connect back to the Unix domain socket within 5 seconds.
Fix: Ensure the socket directory (/tmp/hyperion-<uid>) exists and has read/write permissions for the current user. Verify that the system disk has available inodes and free disk space.
HYP-ERR-002: Address already in use (EADDRINUSE) ▼
Cause: The port specified by -S <IP:PORT> is already bound by another process (e.g. Apache, Nginx, or an existing Hyperion instance).
Fix: Identify and terminate the occupying process using lsof -i :8000, or specify a different port (e.g. hyperion -S 0.0.0.0:8080).
HYP-ERR-003: Memory ceiling reached (Auto-Recycle) ▼
Cause: A worker exceeded HYPERION_MAX_MEMORY_MB (default: 512 MB).
Behavior: Hyperion automatically drained the worker and spawned a fresh replacement without dropping incoming connections. If this happens frequently, check application code for unbounded static arrays or circular object references.
HYP-ERR-004: Uncommitted database transaction detected ▼
Cause: A controller or middleware threw an exception after calling DB::beginTransaction() without an explicit commit() or rollBack().
Behavior: Hyperion automatically rolled back the orphaned transaction before serving the next request, preventing database locks and cross-request state bleeding.
HYP-ERR-005: HTTP 431 Request Header Fields Too Large ▼
Cause: Inbound HTTP request headers exceeded the 64 KB safety threshold (HYP-SEC-02).
Fix: Check upstream reverse proxies (Cloudflare, Nginx) or inspect oversized tracking cookies. Configure upstream cookie pruning if necessary.
Common Questions

Frequently Asked Questions (FAQ)

Key answers for technical leaders, software architects, and DevOps engineers evaluating PHP-Hyperion for production adoption.

Do I need to rewrite any of my existing Laravel or Symfony code? ▼
No. Absolutely zero application code changes are required. Hyperion executes vanilla Laravel 10/11/12, Symfony 5/6/7, and WordPress projects natively. Standard Eloquent models, Blade views, authentication guards, sessions, and multipart uploads operate seamlessly without Octane adapters.
How does Hyperion achieve 208,000+ requests per second? ▼
Hyperion achieves this through a multi-tiered architecture: (1) An asynchronous multi-reactor network loop in Rust using non-blocking mio with SO_REUSEPORT; (2) An in-memory RFC 9111 cache that splices static and cached responses directly from RAM to the client TCP socket in 0.48 ms; and (3) Pre-compiled persistent Zend OPcache workers communicating over 1.04 µs binary length-prefixed IPC sockets.
How is Hyperion different from Laravel Octane (FrankenPHP / RoadRunner / Swoole)? ▼
FrankenPHP embeds PHP into CGo threads (risking thread synchronization bottlenecks and CGo memory contention). Swoole modifies PHP internals with coroutines, causing incompatibilities with third-party C extensions. RoadRunner uses Protobuf RPC over pipes. Hyperion combines an ultra-fast Rust reactor with standard, unadulterated Zend PHP child processes over dedicated Unix domain sockets—guaranteeing 100% thread safety, zero data races, and zero code refactoring.
Does Hyperion work with Livewire 3 and Filament 3 admin panels? ▼
Yes. We have verified Livewire 3 and Filament 3 under high-concurrency test batteries. Because Hyperion enforces strict single-request process isolation and resets container instances between calls, Livewire component dehydrations and Filament form states never bleed across concurrent users.
What happens if a PHP worker encounters a fatal error or crash? ▼
Hyperion’s supervisor watchdog monitors all worker PIDs every 500 ms. If a worker process exits due to an unhandled native extension crash or memory fault, the supervisor immediately respawns and reconnects a pre-warmed worker in under 15 milliseconds. Inbound client TCP connections remain safely queued in kernel backlogs.
Can I deploy Hyperion inside Docker and Kubernetes? ▼
Yes. Hyperion runs as a standard PID 1 container entrypoint. We provide production-ready multi-stage Alpine Dockerfiles, Kubernetes deployment.yaml manifests with liveness/readiness probes, and systemd service unit configurations.
